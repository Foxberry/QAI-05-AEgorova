## T1 — Отображение данных сотрудника, списка больничных листов и сводки

- **Type:** История
- **Priority:** MEDIUM
- **Source Requirements:** FR-01, FR-02, FR-03
- **Dependencies:** нет

**Description:**
Страница «Больничные листы» в личном кабинете авторизованного сотрудника (раздел «Больничные листы») должна отображать:
- данные сотрудника: ФИО, подразделение, должность, руководитель (FR-01);
- список ранее поданных больничных листов за текущий календарный год: ID документа, дата начала, дата окончания, количество календарных дней, статус заявки (FR-02);
- сводку: количество дней нетрудоспособности за год, количество поданных заявок, статус последней заявки (FR-03).

**Acceptance Criteria:**
- AC1.1: Авторизованный сотрудник видит ФИО, подразделение, должность и руководителя.
- AC1.2: Отображается список больничных листов за текущий календарный год с ID документа, датами начала/окончания, количеством календарных дней и статусом.
- AC1.3: Отображается сводка: количество дней нетрудоспособности за год, количество поданных заявок, статус последней заявки.

**Open Questions / Blockers:**
- OQ (FR-02): порядок сортировки списка (по дате подачи / по дате начала) не зафиксирован.
- OQ (FR-03): учитывает ли сводка «количество дней нетрудоспособности» черновики и отклонённые заявки — не определено (связано с FR-15).

## T2 — Форма оформления больничного листа с авторасчётом дней

- **Type:** История
- **Priority:** HIGH
- **Source Requirements:** FR-04, FR-05, FR-06, FR-07
- **Dependencies:** нет

**Description:**
Форма оформления больничного листа должна содержать:
- обязательные поля: ID документа больничного листа (номер ЭЛН), дата начала нетрудоспособности, дата окончания нетрудоспособности, тип нетрудоспособности (выпадающий список: заболевание, травма, уход за ребёнком, карантин, прочее) (FR-04);
- опциональные поля: комментарий сотрудника, прикреплённый файл (скан/справка), отметка «продолжение больничного» со ссылкой на предыдущий ID документа (FR-05);
- поле «Количество календарных дней» рассчитывается автоматически на основании дат начала и окончания и недоступно для ручного редактирования (FR-06);
- кнопки «Сохранить черновик», «Отправить», «Отмена» (FR-07).

Даты вводятся в формате дд.мм.гггг. Учёт ведётся в календарных днях; праздничные и выходные дни включаются в период нетрудоспособности в общем порядке.

**Acceptance Criteria:**
- AC2.1: Форма содержит все обязательные и опциональные поля согласно FR-04, FR-05.
- AC2.2: Поле «Количество календарных дней» рассчитывается автоматически и не редактируется вручную (FR-06).
- AC2.3: Кнопки «Сохранить черновик», «Отправить», «Отмена» присутствуют и работают (FR-07).
- AC2.4: Тип нетрудоспособности выбирается из выпадающего списка (заболевание, травма, уход за ребёнком, карантин, прочее).

**Open Questions / Blockers:**
- OQ (FR-05): ограничения на прикрепляемый файл (формат, размер, количество) не заданы (Ambiguity #9).
- OQ (FR-04): финальный перечень значений типа нетрудоспособности не подтверждён (Ambiguity #11).

## T3 — Поле «ID документа больничного листа»: обязательность, формат, уникальность

- **Type:** История
- **Priority:** HIGH
- **Source Requirements:** FR-08..FR-13, BR-04, BR-05, AC-03, AC-04, AC-05
- **Dependencies:** T2

**Description:**
Реализовать поле «ID документа больничного листа» (номер ЭЛН):
- поле обязательно для заполнения при отправке заявки (FR-08);
- тип поля — строковый (FR-09);
- формат и допустимые символы соответствуют формату номера ЭЛН (по умолчанию — цифры, фиксированная длина по требованиям СФР; уточняется на этапе внедрения) (FR-10);
- проверка уникальности: один ID не может быть использован в двух заявках (FR-11, BR-05);
- при вводе выполняется проверка контрольной суммы / формата (если применимо) с информированием об ошибке (FR-12);
- поле не должно содержать персональные данные, не относящиеся к документу (FR-13).

**Acceptance Criteria:**
- AC3.1: Отправка заявки без ID → ошибка «Укажите ID документа больничного листа.» (AC-03).
- AC3.2: Ввод ID, уже использованного в другой заявке → ошибка «Больничный лист с таким ID уже зарегистрирован.» (AC-04).
- AC3.3: Ввод ID неверного формата → ошибка «Неверный формат ID больничного листа.» (AC-05).

**Open Questions / Blockers:**
- BLOCKER: точный формат номера ЭЛН (длина, символы, контрольная сумма) не определён (Open Question №1, Missing Information №1). Реализация формата требует решения владельца требований/СФР.

## T4 — Валидации дат и пересечений больничного листа

- **Type:** История
- **Priority:** HIGH
- **Source Requirements:** BR-01, BR-02, BR-03, BR-06, BR-07, BR-08, BR-10, AC-01, AC-02, AC-06, AC-07
- **Dependencies:** T2

**Description:**
Реализовать валидации при вводе и отправке заявки на больничный:
- BR-01: дата начала нетрудоспособности не может быть в будущем; допускается «сегодня» или прошедшая дата; при нарушении — блокировка отправки «Дата начала больничного не может быть позже текущей даты.»;
- BR-02: дата окончания не может быть раньше даты начала;
- BR-03: дата окончания не может быть в будущем (для уже закрытого больничного), либо допускается плановая дата окончания — по бизнес-правилу;
- BR-06: заявка не может пересекаться по датам с другим активным больничным листом того же сотрудника;
- BR-07: заявка не может пересекаться с уже утверждённым отпуском без явного согласования HR;
- BR-08: максимальная длительность больничного — согласно законодательству (уточняется, может варьироваться по типу);
- BR-10: не допускается дата начала ранее, чем на N дней от текущей (N настраивается администратором).

**Acceptance Criteria:**
- AC4.1: Дата начала = завтра → ошибка «Дата начала больничного не может быть позже текущей даты.» (AC-01).
- AC4.2: Дата начала = сегодня → заявка отправляется успешно (AC-02).
- AC4.3: Дата окончания < даты начала → ошибка «Дата окончания не может быть раньше даты начала.» (AC-06).
- AC4.4: Пересечение с другим активным больничным → ошибка «Период пересекается с уже зарегистрированным больничным листом.» (AC-07).
- AC4.5: Пересечение с утверждённым отпуском без согласования HR → блокировка/предупреждение по правилу.

**Open Questions / Blockers:**
- OQ (BR-03): разрешать ли открытые больничные с плановой датой окончания (Open Question №3; Conflict #2).
- OQ (BR-06): перечень статусов «активных» больничных для проверки пересечений не определён (Ambiguity #2).
- OQ (BR-07): механика «явного согласования HR» (блокировать/предупреждать/авто-маршрут) не определена (Ambiguity #3, Open Question №5).
- OQ (BR-10): значение N по умолчанию не зафиксировано (Ambiguity #5, Open Question №4).
- OQ (BR-08): максимальная длительность по типам не задана (Ambiguity #4).

## T5 — Правило «продолжение больничного»

- **Type:** История
- **Priority:** MEDIUM
- **Source Requirements:** FR-05, BR-09, AC-08
- **Dependencies:** T3, T4

**Description:**
Реализовать отметку «продолжение больничного» (FR-05) и проверку связывания заявок (BR-09):
- при указании «продолжение больничного» сотрудник указывает ссылку на предыдущий ID документа;
- система проверяет, что предыдущий ID существует, принадлежит сотруднику и его дата окончания + 1 день совпадает с датой начала текущей заявки;
- при нарушении — блокировка отправки с сообщением об ошибке.

**Acceptance Criteria:**
- AC5.1: Отметка «продолжение больничного» присутствует и позволяет указать предыдущий ID.
- AC5.2: Продолжение с несуществующим предыдущим ID → ошибка (AC-08).
- AC5.3: Продолжение с ID другого сотрудника → ошибка.
- AC5.4: Продолжение, у которого дата окончания предыдущего +1 ≠ дата начала текущего → ошибка.

**Open Questions / Blockers:**
- OQ: допустимость пропуска дней между окончанием предыдущего и началом текущего больничного (только +1 день) — соответствует BR-09, неопределённостей нет, кроме механизма указания ID (выпадающий список или ручной ввод).

## T6 — Статусы и workflow заявки на больничный

- **Type:** История
- **Priority:** HIGH
- **Source Requirements:** FR-14..FR-17, FR-20, AC-09, AC-10
- **Dependencies:** T2

**Description:**
Реализовать статусы и workflow заявки на больничный:
- статусы: Черновик, На проверке, Подтверждён, Отклонён, Отменён (FR-16);
- «Отправить» → заявка переходит в статус «На проверке» и направляется в HR (FR-14);
- «Сохранить черновик» → заявка сохраняется в статусе «Черновик» и не участвует в расчётах (FR-15); черновик без обязательных полей допустим, отправка невозможна (AC-09);
- HR может подтвердить или отклонить заявку с указанием причины (FR-17);
- сотрудник может отменить заявку до её подтверждения (FR-20);
- после подтверждения HR заявка уходит в интеграцию и получает статус «Подтверждён» (AC-10).

**Acceptance Criteria:**
- AC6.1: После «Отправить» статус — «На проверке», заявка направлена в HR.
- AC6.2: После «Сохранить черновик» статус — «Черновик», заявка не участвует в расчётах; черновик без обязательных полей допустим, отправка невозможна (AC-09).
- AC6.3: HR может подтвердить заявку с причиной.
- AC6.4: HR может отклонить заявку с причиной.
- AC6.5: Сотрудник может отменить заявку до подтверждения; после подтверждения отмена недоступна.
- AC6.6: После подтверждения HR заявка получает статус «Подтверждён» (AC-10).

**Open Questions / Blockers:**
- OQ (роли, Conflict #3): требуется ли согласование руководителем или больничный сразу уходит в HR (Open Question №7).

## T7 — Уведомления и интеграции (СФР, расчётная система, почта)

- **Type:** История
- **Priority:** MEDIUM
- **Source Requirements:** FR-18, FR-19, FR-21, FR-22, FR-23
- **Dependencies:** T3, T6

**Description:**
- Сотрудник получает уведомление об изменении статуса заявки (FR-18).
- Подтверждённая заявка передаётся в расчётный модуль / внешнюю систему (СФР, 1С ЗУП и т.п.) для начисления пособия (FR-19, FR-22).
- Интеграция с внешним сервисом проверки ЭЛН (СФР/ФСС) для валидации ID документа — при наличии технической возможности (FR-21).
- Интеграция с корпоративной почтой / мессенджером для уведомлений (FR-23).

**Acceptance Criteria:**
- AC7.1: При изменении статуса заявки сотрудник получает уведомление (FR-18).
- AC7.2: Подтверждённая заявка передаётся в расчётный модуль / внешнюю систему (FR-19, AC-10).
- AC7.3: При наличии сервиса СФР/ФСС выполняется онлайн-валидация ID документа (FR-21).
- AC7.4: Уведомления отправляются через корпоративную почту / мессенджер (FR-23).

**Open Questions / Blockers:**
- OQ (FR-21, Open Question №2): нужна ли интеграция с СФР для онлайн-валидации ЭЛН или проверка выполняется вручную HR.
- OQ (FR-22, Open Question №8): какие API доступны у внешних систем, в каком режиме (online/offline).
- OQ (FR-18/FR-23, Ambiguity #10): конкретный канал уведомлений не указан.
- BLOCKER: интеграции зависят от решений по внешним системам (СФР, 1С ЗУП).

## T8 — Нефункциональные требования

- **Type:** История
- **Priority:** MEDIUM
- **Source Requirements:** NFR-01..NFR-06
- **Dependencies:** T2

**Description:**
Обеспечить выполнение нефункциональных требований:
- NFR-01: время отклика формы — не более 1.5 сек при 500 одновременных пользователях;
- NFR-02: данные о нетрудоспособности — персональные данные, хранение в соответствии с 152-ФЗ, шифрование TLS 1.2+ и AES-256;
- NFR-03: аудит всех действий по заявке (создание, изменение, отправка, подтверждение/отклонение) с указанием пользователя, времени, IP;
- NFR-04: адаптивность — десктоп, планшет, смартфон (iOS/Android);
- NFR-05: доступность (SLA) — 99.9% в рабочее время;
- NFR-06: резервное копирование ежедневно, восстановление на любую точку за последние 30 дней.

**Acceptance Criteria:**
- AC8.1: Время отклика формы ≤ 1.5 сек при 500 одновременных пользователях (NFR-01).
- AC8.2: Данные защищены: TLS 1.2+, AES-256, соответствие 152-ФЗ (NFR-02).
- AC8.3: Все действия по заявке логируются с пользователем, временем и IP (NFR-03).
- AC8.4: Страница корректно отображается на десктопе, планшете и смартфоне (iOS/Android) (NFR-04).
- AC8.5: Доступность 99.9% в рабочее время (NFR-05).
- AC8.6: Резервное копирование ежедневно, восстановление на любую точку за 30 дней (NFR-06).

**Open Questions / Blockers:**
- OQ: целевые показатели производительности (NFR-01) требуют подтверждения нагрузочным тестированием на этапе внедрения.
- OQ (NFR-02): конкретные компоненты шифрования на уровне хранения данных — решение архитектуры/ИБ.
